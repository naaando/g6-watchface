# G6 watchface samples

The two `0.0_AM05_*.bin` files were copied read-only from the AuraFit cache on the Galaxy A54:

`/sdcard/Android/data/com.sma_aurafit/cache/dial/`

`0.0_G6_captured_618808.bin` was **not** read from the cache. It was captured passively
off the Bluetooth link while AuraFit pushed it to the G6, by `ble-capture/parse_btsnoop.py`.
See "Passive capture over Bluetooth" below.

The extensionless files with the same names contain the thumbnail URLs from AuraFit's cache. `decoded_*/` contains the PNG layers and `dial_desc.json` generated by Fogg's `comp_decomp.py`.

`roundtrip_*.bin` was recompiled from the decoded layers. All three dials now recompile **byte-identical** to the originals, so a decode/compile round trip is lossless. That required one fix in `comp_decomp.py`: the metadata now records the verbatim block-type byte as `raw_type`, because the symbolic `type` name is lossy (it strips the 0x80 RGBA bit and falls back to `unknown_xx` for codes the tool does not model, so recompiling rewrote the captured dial's `0xA1` block as `0x81`). No compiled file has been sent to the watch.

## Passive capture over Bluetooth

`0.0_G6_captured_618808.bin` came out of a 32.4 s BLE session on the Galaxy A54 while AuraFit
downloaded that watchface to the G6. The transfer does not send a bare BIN: each ATT write
carries one proprietary JieLi frame

```
ab | type | len_hi len_lo (big endian) | ?? | ?? | body...
0     1       2             3           4    5    6 .. 6+len
```

where `type` `0x01` is a data frame and `0x11` is an acknowledgement. A data frame body is a
12-byte per-frame prologue followed by 1018 file bytes; the last two bytes of the prologue are
the running file offset as a **wrapping 16-bit counter** (it rolls over at 65536), so they
double as an integrity check. The capture ran 608 data + 608 ack frames, offsets contiguous
with no gaps, 607 x 1018 + 882 = 618,808 bytes — which matches the size predicted by the HK89
header exactly. The `0xA1` block type mentioned above is one of the 16 layers in this dial.

The capture was passive only. Nothing was ever written back to the watch, and the capture
starts only after the user has already begun the download in AuraFit.

## G6 connection finding (2026-09-27)

The user removed the G6 from AuraFit and factory-reset it to make it discoverable to another app. In pairing mode, the official JieLi Watch Test Tool found the G6 and completed RCSP initialization over BLE. Its log identified the JieLi watch SDK flag. The tool then disconnected because its `WatchManager` requires mandatory-upgrade or external-flash-transfer support for its watch operations, and the G6 reported neither. This limits the **test tool's** watchface browser/transfer path; it does not imply the G6 cannot use custom dials through AuraFit's own path. The tool automatically synchronized the time during connection. No watchface file or firmware was transferred. After that app could not handle watch operations, the user paired the G6 with AuraFit again; AuraFit's device page then showed the G6 connected with 62% battery.

Reproduce a local decode with Python, Pillow, and NumPy:

```sh
python Fogg/comp_decomp.py trek-watchfaces/0.0_AM05_G6_11359.bin trek-watchfaces/decoded_11359
python Fogg/comp_decomp.py trek-watchfaces/0.0_AM05_G6_11448.bin trek-watchfaces/decoded_11448
python Fogg/comp_decomp.py trek-watchfaces/0.0_G6_captured_618808.bin trek-watchfaces/decoded_captured_618808
```
